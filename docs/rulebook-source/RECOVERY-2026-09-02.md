## 2. Acknowledgment county (R21) — unfilled requirement, located

`CONTEXT.md:328` requires acknowledgment-county and recording-county as **distinct captures**.
Repo-wide search finds no column, no contract field, no extraction path: the only non-license hits
are prose (`docs/PRD.md:229`, `docs/backend/IMPLEMENTATION_PLAN.md:910`, `CONTEXT.md:309/312`).

**Where it lives: document grain, not jurisdiction.** Justification:

- The notary block is *per instrument*. One package routinely mixes instruments acknowledged in
  different counties (and states) while every one of them recorded in the subject county.
- A jurisdiction-grain field would be structurally unable to represent the distractor it exists to
  catch — a single order-level value cannot disagree with itself.
- R24 names the acknowledgment as a **document-boundary terminator** ("legal description +
  signatures + acknowledgment + recording info"), so it is already segmented at document grain.
- `recording_county` is likewise document-grain: it is read from that document's clerk stamp.

**Specified shape** (both nullable, both provenance-carrying, both honouring the two NA states —
`NOT_PRESENT` for an instrument with no notary block, `PRESENT_UNREADABLE` for an illegible one;
never collapsed, never `null`-derived):

    documents.recording_county        -- from the clerk/recording stamp. Reported.
    documents.acknowledgment_county   -- from the notary block. CAPTURED, NEVER RENDERED.
    documents.acknowledgment_state    -- same block; the distractor is often out-of-state.

The render layer must have no path to `acknowledgment_county`. That refusal is a product
requirement, so it is a test, not a convention: a Playwright/renderer assertion that the value is
absent from every emitted report shape, plus a validator that fires `needs_review` when
`acknowledgment_county` is present, differs from `recording_county`, and the county field of the
report was filled from anything other than the stamp.

Status: **filed, not implemented.** It is a schema-v2 delta owned by the backend, and it cannot be
built past the R13–R24 text gap being `OPEN` at the level of exact wording.

## 3. Canonical jurisdiction spelling — ruling

Three vocabularies, no shared referent:

| Spelling | Where | Kind |
|---|---|---|
| `clayton-ga` | `apps/web/src/features/jurisdiction/jurisdictionCodes.ts:7,14`; `packages/mocks/src/data.ts:141+` | live code |
| `GA-CLAYTON` | `docs/superpowers/plans/backend/proposals/NORMALIZATION-AUDIT.md:502,532,542` | proposal only |
| `FL`, `FL/Broward` | `services/core-api/tests/test_rules_contract_parity.py:149,173` | test fixtures |

**Does runtime code parse the slash grammar? No.** `jurisdiction_scope` is declared
`Text, nullable=True` (`services/core-api/src/titlepipe_core/db/models.py:370`), surfaced as
`str | None` (`api/schemas/rules.py:96`), and has **zero** other references in `services/core-api/src`
or `libs`. No `split("/")`, no state/county decomposition, no comparison against an order's
jurisdiction anywhere. `db/rules.py` mentions jurisdiction only in a docstring (`:141`). So the
column is currently an opaque display string, and the cost of fixing the vocabulary is **low** —
it is a data/seed change plus fixtures, not a parser rewrite.

**Ruling — canonical form is `clayton-ga` (lowercase `county-state`).** Reasons, in order of weight:

1. It is the only spelling with running code behind it, including `DEFAULT_JURISDICTION_CODE`
   and every mock order. `GA-CLAYTON` exists in exactly one unmerged proposal.
2. It is already URL-safe: `GET /api/jurisdictions/{code}`
   (`apps/web/src/shared/jurisdictionQueries.ts:11`) would need escaping for a slash form.
3. Display strings are derived, never stored — `jurisdiction_label` is already computed
   (`packages/mocks/src/design.ts:438`), consistent with the audit's own recommendation at
   `NORMALIZATION-AUDIT.md:502`.

Statewide scope keeps the bare state segment as a **prefix-free distinct value**: `ga`, not `GA`.
`FL/Broward` becomes `broward-fl`; `FL` becomes `fl`. Because nothing parses the value, the
migration is a rewrite of the two fixtures at `test_rules_contract_parity.py:149,173` (and 525)
plus a seed pass — no code path changes.

Matching rule (server-side, when scope resolution is implemented): a rule with scope `null` is
global; scope `ga` binds every `*-ga`; scope `clayton-ga` binds only that county. That is
**prefix-suffix matching on the state segment**, and it is the one piece of grammar the codebase
will need to add. It is cheap precisely because no competing grammar is in the way today.
